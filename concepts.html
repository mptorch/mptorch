Formats and rounding#

This page presents the fundamentals that the rest of the documentation relies on:

  • what a number format is;

  • which formats MPTorch implements: scalar formats, and block formats that share a scale among their elements;

  • what each rounding mode does;

  • which arithmetic the simulation rounds in;

  • the equations the kernels follow.

Every example on this page comes from a run.

The simulation model#

MPTorch never computes in a narrow format. Every operation (a product, an addition, an activation) is carried out in an IEEE binary float, the carrier. Its result is then rounded to the target format \(F\) with a rounding mode \(\circ\):

\[\tilde{x} = Q_{F,\circ}(x).\]

For an elementwise step, such as rounding a weight tensor, that is all there is, and it is what the quantizers do (see Quantizers). A reduction such as a dot product has intermediate results, and each of them can be rounded. Which intermediates are rounded, and to which format, is the arithmetic that the kernels simulate (see Quantized numerical kernels). For one output element of a matrix product, this can look like:

\[c_{ij} = \sum_{k} a_{ik}\, b_{kj} \quad\longrightarrow\quad s_{k} = Q_{\text{acc}}\big(s_{k-1} + Q_{\text{mul}}(a_{ik} b_{kj})\big).\]

The carrier (see Carriers) has far more precision and range than the simulated format. Computing in it and rounding once therefore usually gives the correctly rounded result of the simulated operation, the number a machine working natively in \(F\) would produce. This holds for every format the carrier can hold.

BinaryK: the IEEE P3109 formats#

BinaryK is the family of binary floating-point formats defined by IEEE P3109, the upcoming Standard for Arithmetic Formats for Machine Learning (Fitzgibbon, Wintersteiger and Sarnoff give an overview of the draft). P3109 parameterizes a format by four things: its bitwidth \(K\), its precision \(P\), its signedness, and its domain, which says whether it has infinities. A format is named after them. Binary8p4se is the 8-bit signed (s) format with 4 bits of precision in the extended (e) domain, and Binary8p4sf is its finite-domain (f) twin.

The bits are laid out as in an IEEE 754 binary float. A value has a sign \(s\), a biased exponent \(e\) of \(E\) bits and a stored mantissa \(m\) of \(P-1\) bits. The \(P\)-th bit of precision is the implicit leading one. Its value is

\[x = (-1)^s \cdot \Big(1 + \frac{m}{2^{P-1}}\Big) \cdot 2^{\,e - \text{bias}} \qquad (1 \le e \le 2^E - 1)\]

for normal numbers, and

\[x = (-1)^s \cdot \frac{m}{2^{P-1}} \cdot 2^{\,1 - \text{bias}} \qquad (e = 0)\]

for subnormal numbers, which fill the gap between zero and the smallest normal with the same absolute spacing. You give the total width \(K\) and the precision \(P\). The exponent width follows: \(E = K - P\) for a signed format, and \(E = K - P + 1\) for an unsigned one, which has no sign bit. is_signed is P3109’s signedness, and the domain is set together with the saturation mode (below).

A few consequences are worth keeping in mind:

  • Within one binade \([2^q, 2^{q+1})\) there are \(2^{P-1}\) representable values, spaced \(2^{q-P+1}\) apart. This spacing is the unit in the last place (ulp). The relative spacing is therefore between \(2^{-P}\) and \(2^{1-P}\): neighbouring values are about 6-12 % apart with \(P = 4\) (E4M3’s precision) and 12-25 % apart with \(P = 3\) (E5M2’s). Rounding to nearest moves a value by at most half of that.

  • The largest finite value depends on the domain. In P3109’s extended domain (the default) the last code of the top binade is \(\infty\), and the largest finite value is \((2 - 2^{2-P}) \cdot 2^{\,2^E - 1 - \text{bias}}\). In the finite domain that code is a number, and the largest finite value is \((2 - 2^{1-P}) \cdot 2^{\,2^E - 1 - \text{bias}}\). Both hold for a signed format with \(P \ge 3\). Subnormals, saturation and sign says how to choose the domain, and Relation to IEEE P3109 gives the rules for the other formats.

  • The smallest normal is \(2^{1 - \text{bias}}\) and the smallest subnormal \(2^{1 - \text{bias} - (P-1)}\).

  • bias defaults to P3109’s, the middle of the exponent range: \(2^{E-1}\), which is \(2^{K-P-1}\) for a signed format and \(2^{K-P}\) for an unsigned one. Either way 1.0 is encoded at the middle code point. For the same exponent width, IEEE 754’s bias is \(2^{E-1} - 1\), one less. P3109 fixes the bias rather than the largest exponent, so that adding or removing the infinities moves no finite value. Pass bias= explicitly for a format outside P3109, such as the nearest spellings of the OCP 8-bit formats.

  • A BinaryK format uses every exponent code for finite values, where IEEE 754 reserves the top one for infinities and NaNs. Take a BinaryK format with the IEEE bias and the same exponent and mantissa widths as an IEEE 754 format (float16, float32). It agrees with that format on every value up to its largest finite one, and then continues for one more binade. So no BinaryK format is float16, bfloat16 or float32 (see The IEEE 754 dtypes are not P3109 formats). The OCP formats compare the same way, and the tutorial checks it exhaustively (see Tutorial: training in 8-bit floating point): E5M2 is laid out the IEEE way, so its BinaryK spelling also goes a binade past it, while E4M3 spends its top exponent field on numbers and is matched on every finite value.

The following run constructs P3109’s two signed 8-bit formats with 4 and 3 bits of precision, derives their ranges from the formulas above, and checks them against the quantizer in both domains. Each boundary value is a fixed point of the rounding in the domain that has it. For example, \(10^{30}\) overflows to \(\infty\) in the extended domain and to the largest finite value in the finite one.

"""BinaryK: IEEE P3109's K-bit floating-point formats with P bits of precision."""

import torch

from mptorch import BinaryK, SaturationMode
from mptorch.quant import Quant

torch.manual_seed(0)

binary8p4 = BinaryK(8, 4)  # P3109 Binary8p4se: 1 sign, 4 exponent, 3 stored mantissa bits
binary8p3 = BinaryK(8, 3)  # P3109 Binary8p3se: 1 sign, 5 exponent, 2 stored mantissa bits


def describe(f: BinaryK) -> None:
    exp_bits = f.K - f.P if f.is_signed else f.K - f.P + 1
    top_binade = 2.0 ** (2**exp_bits - 1 - f.bias)
    max_extended = (2 - 2 ** (2 - f.P)) * top_binade  # the last code is infinity
    max_finite = (2 - 2 ** (1 - f.P)) * top_binade  # the last code is a number
    min_normal = 2.0 ** (1 - f.bias)
    min_subnormal = 2.0 ** (1 - f.bias - f.man_bits)
    print(f"{f}")
    print(f"  exponent bits {exp_bits}, mantissa bits {f.man_bits}, bias {f.bias}")
    print(f"  largest finite  {max_extended:g} (extended domain), {max_finite:g} (finite domain)")
    print(f"  smallest normal {min_normal:g}")
    print(f"  smallest subnormal {min_subnormal:g}")
    # The quantizer agrees with the formulas: each value is a fixed point in the
    # domain that has it, and 1e30 overflows -- to infinity in the extended
    # domain, to the largest finite value in the finite one.
    probe = torch.tensor([max_extended, max_finite, min_normal, min_subnormal, 1e30])
    for sat in (SaturationMode.SAT_NONE, SaturationMode.SAT_FINITE):
        q = Quant(BinaryK(f.K, f.P, bias=f.bias, saturation=sat))
        print(f"  {sat.name:<11}{q(probe).tolist()}")

The IEEE 754 dtypes are not P3109 formats#

float16, bfloat16 and float32 are not exactly representable as P3109 formats in either domain, nor as BinaryK formats with any other bias. The two standards spend the code points of the same layout differently:

  • IEEE 754 reserves the whole top exponent field (\(2^{P-1}\) codes of each sign) for \(\pm\infty\) and the NaNs. It gives zero two encodings, \(+0.0\) and \(-0.0\).

  • P3109 spends one code of each sign on \(\pm\infty\), and only in the extended domain. Every other code of the top field is a finite value. A signed format has a single, unsigned zero, and the encoding IEEE 754 would read as \(-0.0\) is its one NaN.

  • P3109’s default bias, \(2^{E-1}\), is one more than IEEE 754’s for the same exponent width (\(2^{E-1}-1\)).

A bias can therefore line up at most one end of the range with that of the closest IEEE 754 dtype, and the special values never match. For float16, for instance:

  • With P3109’s bias, Binary16p8 and Binary32p24 lose the dtype’s largest value to \(+\infty\) in the extended domain and match it in the finite one. They add \(2^{P-1}\) values below the dtype’s smallest normal, down to \(2^{-134}\) and \(2^{-150}\).

The two OCP 8-bit formats relate to their BinaryK rows differently.

E5M2 reserves its top exponent field as IEEE 754 does. So BinaryK(8, 3, bias=15) relates to it as BinaryK(16, 11, bias=15) relates to float16 above: it has every finite value of E5M2 and one binade more. E5M2’s largest finite value is \(57344\). The BinaryK format adds \(65536\), \(81920\) and \(98304\) of each sign. Under SAT_FINITE it also adds \(114688\), the code that is \(\pm\infty\) in the extended domain.

E4M3 spends its top exponent field on finite values, as P3109 does. So BinaryK(8, 4, bias=7) has exactly E4M3’s finite values, up to \(448\). Only the special codes differ: the BinaryK format has \(\pm\infty\) where E4M3 has its two NaNs, and its one NaN where E4M3 has \(-0\). The difference shows in what an overflow returns. E4M3 has no infinity, and PyTorch’s conversion to torch.float8_e4m3fn saturates at \(\pm 448\). BinaryK(8, 4, bias=7) returns:

  • \(\pm\infty\) under SAT_NONE, the default.

  • \(\pm 448\) for a finite input under SAT_PROPAGATE, which leaves an infinite input infinite.

  • \(\pm 448\) for every input under SAT_FINITE_EXTENDED, infinite ones included. This is PyTorch’s result for every float32 input, except that a zero is always \(+0\).

  • \(\pm 480\) under SAT_FINITE. Its finite domain turns the infinity’s code into a number, which E4M3 does not have.

In MPTorch these differences show up in two places:

  • Quantizing to one of the dtype-layout rows is not the dtype’s own conversion. A value between the dtype’s largest finite value and the row’s stays finite, where the dtype would store \(\pm\infty\). And \(-0.0\) comes back as \(+0.0\).

  • The range checks flag these formats:

    • BinaryK(16, 8, bias=127) and BinaryK(32, 24, bias=127) reach \(2^{128}\). On a float32 tensor they warn that they outrun binary32.

    • Binary16p8 and Binary32p24 warn about their bottom there (see What the carrier can hold). A float64 tensor holds all four.

    • BinaryK(16, 11, bias=15), as the format of a GEMM’s result over float16 operands, warns that it reaches past float16 (see What a narrower tensor can store).

Subnormals, saturation and sign#

Two enums decide what happens at the ends of the range. Both are properties of the format, so two formats in one computation can differ in them.

SubnormalsMode decides the bottom of the range:

SUBNORMALS

Gradual underflow, as in IEEE 754 and in P3109, whose formats all have subnormals once \(P > 1\). The exponent code 0 encodes the subnormal numbers, down to \(2^{1-\text{bias}-(P-1)}\).

NORMALS

No subnormals, which takes the format outside P3109. The exponent code 0 encodes only the zero, and the smallest value is the smallest normal, \(2^{1-\text{bias}}\).

EXTENDED_NORMALS

No subnormals either, and also outside P3109. The exponent code 0 encodes one more binade of normal numbers, above \(2^{-\text{bias}}\), with the full mantissa. Its first code is still the zero, so the smallest value is one step above the power of two, \((1 + 2^{1-P})\, 2^{-\text{bias}}\).

Below its smallest value every mode rounds the same way: to zero or to that value, as the rounding mode decides (Relation to IEEE P3109 gives the rule). A value is flushed to zero only if the rounding mode says so. Under round-to-nearest, that is when it is nearer to zero than to the smallest value.

SaturationMode and Domain decide the top. P3109 chooses two things here, separately:

  • the domain: whether the format spends its top code of each sign on \(\pm\infty\) (extended) or on a number (finite);

  • the saturation mode: what an operation does with a result beyond the largest finite value.

The finite domain admits only SatFinite, which leaves four valid pairs. Each pair is one member of SaturationMode:

SAT_FINITE

P3109’s SatFinite, in the finite domain. Everything is clamped to the largest finite value, which here includes the top mantissa code. This applies to a finite input that overflows and to an infinite input, so the output never contains an infinity. NaN inputs pass through unchanged.

SAT_FINITE_EXTENDED

P3109’s SatFinite, in the extended domain. The format keeps its infinity codes, so its largest finite value is the same as under SAT_PROPAGATE and SAT_NONE. Everything is clamped to it, infinite inputs included, as under SAT_FINITE.

SAT_PROPAGATE

P3109’s SatPropagate, in the extended domain. A finite input that overflows is clamped to the largest finite value, which excludes the top mantissa code. This includes an input that rounds onto that code, like 480 in the run below. An infinite input stays infinite.

SAT_NONE

P3109’s SatNone, in the extended domain, and the default. An input that rounds past the largest finite value becomes \(\pm\infty\). P3109 rounds before it saturates, so this happens under every rounding mode, including those for which IEEE 754 stops at the largest finite value, such as rounding toward zero (the run’s SAT_NONE, RZ line).

A BinaryK or SuperFP can also name the pair as P3109 does, with domain= next to saturation=. BinaryK(8, 4, saturation=SAT_FINITE, domain=Domain.EXTENDED) is stored as saturation=SAT_FINITE_EXTENDED, and the two spellings make equal formats. If domain is left out, it follows from the mode: finite for SAT_FINITE and extended otherwise. domain=Domain.FINITE with any other mode raises. The flat functions of the schema tier take no format object, so they name the pair with the SaturationMode member alone.

"""What happens at the two ends of the range: subnormals and saturation."""

import torch

from mptorch import BinaryK, Domain, RoundMode, SaturationMode, SubnormalsMode
from mptorch.quant import Quant

torch.set_printoptions(precision=6, sci_mode=False)

# Small values, in E4M3's layout (bias 7): the smallest normal is 2**-6. Under
# EXTENDED_NORMALS the binade below it holds normals as well, but its
# mantissa-zero code is still the zero -- so 2**-7 is not one of them, and
# that binade starts at 1.125 * 2**-7.
small = torch.tensor([2.0**-5, 2.0**-6, 2.0**-7, 2.0**-8, 2.0**-9, 2.0**-10])
print("input               ", small.tolist())
for mode in SubnormalsMode:
    q = Quant(BinaryK(8, 4, bias=7, subnormals=mode))
    print(f"{mode.name:<20}", q(small).tolist())

# Large values, same layout: the top code, 480, is a number in the finite
# domain (SAT_FINITE) and infinity in the extended one (the other three),
# whose largest finite value is 448.
large = torch.tensor([448.0, 480.0, 500.0, 1e6, float("inf"), -float("inf"), float("nan")])
print("\ninput               ", large.tolist())
for mode in SaturationMode:
    q = Quant(BinaryK(8, 4, bias=7, saturation=mode))
    print(f"{mode.name:<20}", q(large).tolist())

# As in P3109, rounding comes before saturation, so SAT_NONE overflows to infinity
# even when rounding toward zero, where IEEE 754 would stop at 448.
q = Quant(BinaryK(8, 4, bias=7), RoundMode.RZ)
print(f"{'SAT_NONE, RZ':<20}", q(large).tolist())

# P3109's own spelling of the pair: SatFinite in the extended domain is
# SAT_FINITE_EXTENDED, and the two spellings make the same format.
f = BinaryK(8, 4, bias=7, saturation=SaturationMode.SAT_FINITE, domain=Domain.EXTENDED)
print(
    f"\n{f.saturation.name}, {f.domain.name}:",
    f == BinaryK(8, 4, bias=7, saturation=SaturationMode.SAT_FINITE_EXTENDED),
)

# An unsigned format has no sign bit, so negative inputs collapse to zero and
# the freed bit goes to the exponent (bias 16 instead of 8).
u = BinaryK(8, 4, is_signed=False)
print(f"\n{u}")
print("unsigned            ", Quant(u)(torch.tensor([-3.0, -0.001, 0.0, 3.0, 3000.0])).tolist())

  • It has five exponent bits and the default bias \(2^{K-P} = 16\), where the signed format has four and \(2^{K-P-1} = 8\). Its normal exponents therefore run from \(-15\) to \(15\) instead of \(-7\) to \(7\).

Relation to IEEE P3109#

The sections above introduced P3109 one notion at a time: how it names a format after its parameters, its default bias, its two domains and its three saturation modes. This section puts them side by side and says in what sense a BinaryK is a P3109 format. It covers, in order:

  • which MPTorch argument stands for which notion of the standard.

  • the rule for the largest finite value, which the earlier sections stated only for a signed format with \(P \ge 3\).

  • how the correspondence is tested.

  • the two ways in which MPTorch departs from the standard.

Every parameter of a P3109 format, and each of its saturation and rounding modes, has a counterpart among the arguments of BinaryK and MPTorch’s enums. A BinaryK(K, P) left at its defaults is therefore the P3109 format with that bitwidth and precision, signed and in the extended domain, for every width the standard admits. The rounding modes are introduced further down (see Rounding modes); their rows are listed here so that the whole correspondence is in one table.

The top of the range is counted in P3109’s code points. The top binade has \(2^{P-1}\) codes:

  • In the extended domain, the last one is \(+\infty\).

  • An unsigned format spends its last one on NaN and, in the extended domain, the one below that on \(+\infty\).

The largest finite value is the highest code left: \(224\) for Binary8p4se, \(240\) for Binary8p4sf and \(53248\) for Binary8p4ue. With \(P \le 2\) the reserved codes can outnumber the top binade’s, which moves the largest finite value a binade or two lower. A finite result above it saturates in every rounding mode.

dev/benchmarks/formats/binaryK_values.py prints the whole code-point table of a format: every value, one per line, infinities and NaN included. With --verify it quantizes each value and checks that the kernel returns it unchanged. dev/benchmarks/formats/superfp_values.py does the same for SuperFP.

Two test files compare the formats to the standard:

  • tests/test_binaryk_quantize.py checks the six deterministic modes against gfloat, a reference implementation of P3109, below the top of the range.

  • tests/test_binaryk_p3109.py checks the top itself, against a transcription of the paper’s definitions: every precision of the 3- to 8-bit formats, signed and unsigned, in all three saturation modes. gfloat is not used there because it overflows the IEEE 754 way under directed rounding.

MPTorch departs from the standard in two ways.

By extension. Three options describe formats that P3109 does not define: a bias other than the default, the NORMALS and EXTENDED_NORMALS subnormal modes, and the widths the standard excludes (it requires \(K \ge 3\), and \(P < K\) for a signed format). These options are what make E4M3’s finite values reachable, as well as the nearest representations of E5M2 and the IEEE 754 dtypes (see The IEEE 754 dtypes are not P3109 formats).

The two extra subnormal modes change only the bottom of the range. Both concern the \(2^{P-1}\) codes of each sign whose exponent field is zero. SUBNORMALS spends these on the zero and the \(2^{P-1} - 1\) subnormals. The other two modes use them differently:

  • NORMALS leaves all of them unused except the zero, so the smallest positive value is the smallest normal, \(2^{1-\text{bias}}\).

  • EXTENDED_NORMALS spends them on one more binade of normals, \([2^{-\text{bias}}, 2^{1-\text{bias}})\), directly below the smallest normal. The mantissa-zero code of that binade does not encode \(2^{-\text{bias}}\). It remains the zero (and, with the sign bit set, the NaN), as in every other BinaryK format. The binade therefore holds \(2^{P-1} - 1\) values. The smallest is one step above the power of two at its foot, \((1 + 2^{1-P})\, 2^{-\text{bias}}\). With \(P = 1\) the binade holds no values.

Let \(x_{\min}\) be the smallest positive value of the format: \(2^{1-\text{bias}-(P-1)}\) under SUBNORMALS, and the two values in the list above under the other modes. Below \(x_{\min}\) all three modes round the same way. An input \(x\) with \(0 < |x| < x_{\min}\) has two candidates for its magnitude, zero and \(x_{\min}\), and the rounding mode picks between them (see Rounding modes):

  • RNE and RNA take the nearer one. On a tie, \(|x| = x_{\min} / 2\), RNE takes the zero and RNA takes \(x_{\min}\).

  • RU, RD and RZ take the candidate in their own direction.

  • RO takes \(x_{\min}\), the nonzero candidate.

  • SR takes \(x_{\min}\) with probability \(|x| / x_{\min}\), and the zero otherwise.

By simulating values rather than code points. A result is a value of the carrier, not an encoding, so P3109’s single NaN is whichever NaN came in. P3109’s single zero is unsigned, and here MPTorch does follow the standard: every zero the kernels return is \(+0.0\), whether it came from \(-0.0\) or from a negative value that rounded to zero. The same holds for SuperFP.

SuperFP: precision at the top, range below#

SuperFP is the second format family the kernels implement. It has the same three fields as a binary float (man_bits, exp_bits, bias), but only the top normal_binades binades carry a mantissa. The codes of the remaining \(2^{\mathrm{exp\_bits}} - \mathrm{normal\_binades}\) binades, \(2^{\mathrm{man\_bits}}\) codes each, are reinterpreted. The first is the zero. The others are further powers of two below the normal region, one per code: numbers with an implicit mantissa of exactly 1. With \(e_{\max} = 2^{\mathrm{exp\_bits}} - 1 - \text{bias}\), the three regions are

\[\begin{split}\begin{aligned} \text{normal:} &\quad [2^{\,e_{\max} - b + 1},\; 2^{\,e_{\max}+1}), && \text{full mantissa} \\ \text{supernormal:} &\quad [2^{\,e_{\max} - b + 2 - n},\; 2^{\,e_{\max} - b + 1}), && \text{powers of two only} \\ \text{underflow:} &\quad \text{below that}, && \text{flushed to zero} \end{aligned}\end{split}\]

where \(b = \mathrm{normal\_binades}\) and \(n = (2^{\mathrm{exp\_bits}} - b)\, 2^{\mathrm{man\_bits}}\) is the number of reinterpreted codes, of which \(n - 1\) are supernormals. There are no subnormals. The bias has no default: it is part of the format’s design and must be given. In the supernormal region, rounding acts on the exponent: to nearest, \(3 = 2^{1.58}\) becomes \(4\).

"""SuperFP: precision at the top of the range, dynamic range below it."""

import torch

from mptorch import SuperFP
from mptorch.quant import Quant

# 3 mantissa bits, 4 exponent bits, bias 7 -- the same widths as E4M3 -- but
# only the top 2 binades keep their mantissa. The codes that would have
# encoded the other 14 binades' mantissas become 14 * 2**3 = 112 further
# powers of two below them.
f = SuperFP(man_bits=3, exp_bits=4, normal_binades=2, bias=7)
q = Quant(f)

max_exp = 2**f.exp_bits - 1 - f.bias  # 8: the top binade is [2**8, 2**9)
normal_lo = max_exp - f.normal_binades + 1  # 7
super_lo = normal_lo - (2**f.exp_bits - f.normal_binades) * 2**f.man_bits + 1  # -104
print(f"{f}")
lo, hi = 2.0**normal_lo, 2.0 ** (max_exp + 1)
print(f"  normal region      [2^{normal_lo}, 2^{max_exp + 1})  = [{lo:g}, {hi:g})")
print(f"  supernormal region [2^{super_lo}, 2^{normal_lo})  = powers of two only")
print(f"  below 2^{super_lo - 1} = {2.0 ** (super_lo - 1):g}: flushed to zero")

# In the normal region the mantissa is kept ...
x = torch.tensor([128.0, 144.0, 160.0, 176.0, 300.0, 448.0, 511.0])
print("\nnormal region     ", x.tolist())
print("quantized         ", q(x).tolist())
# ... below it only the power of two survives (3 is rounded to 4: round to
# nearest is taken on the exponent, and 3 = 2**1.58 is nearer to 2**2) ...
x = torch.tensor([1.0, 1.5, 3.0, 100.0, 2.0**-20, 3.0 * 2**-50])
print("\nsupernormal region", x.tolist())
print("quantized         ", q(x).tolist())
# ... and far below, the flush to zero.
x = torch.tensor([2.0**-104, 2.0**-105, 2.0**-106])
print("\nunderflow         ", x.tolist())

FixedPoint: one step across the range#

FixedPoint is a fixed-point format, defined as in Gupta et al., Deep Learning with Limited Numerical Precision. A word of wl bits holds an integer \(k\), and its value is \(k \cdot 2^{-\text{fl}}\). Every value is a multiple of the same step, \(2^{-\text{fl}}\), so the grid is as fine at the top of the range as near zero, and there is no exponent field. With \(n\) magnitude bits (wl - 1 in a signed format, wl in an unsigned one), the range is

\[\begin{split}\begin{aligned} \text{two's complement (the default):} &\quad [-2^{\,n-\text{fl}},\; 2^{\,n-\text{fl}} - 2^{-\text{fl}}] \\ \text{symmetric:} &\quad [-(2^{\,n-\text{fl}} - 2^{-\text{fl}}),\; 2^{\,n-\text{fl}} - 2^{-\text{fl}}] \\ \text{unsigned:} &\quad [0,\; 2^{\,n-\text{fl}} - 2^{-\text{fl}}] \end{aligned}\end{split}\]

fl can be any integer: negative for a step larger than 1, or larger than wl for a format that holds only fractions.

  • Every rounding mode applies (Rounding modes). Under RNE a tie goes to the even integer code.

  • Below the step, the two candidates are zero and the step itself, as for a BinaryK format below its smallest subnormal.

  • A result past either end saturates to that end, and so does an infinity: the word has no code for one, so the format has no saturation mode.

  • A NaN passes through, a negative input to an unsigned format becomes zero, and the one zero is \(+0.0\), as for BinaryK.

  • Under SR the random bits are added directly below the step, so the probability is exactly the one Stochastic rounding states, at every prng_bits: none gives RZ.

  • The magnitude bits must fit the carrier’s precision, and with prng_bits they share it: at most 24 bits in all in binary32 and 53 in binary64 (Carriers).

  • There is no fixed-point arithmetic inside a SplitMac or a FusedMac yet, and they refuse a FixedPoint, as a Palette does. As the element of a block format, though, it is multiplied by the block GEMM (Block floating point).

The carrier bounds a fixed-point format the way it bounds a float format (What the carrier can hold), with one difference: the format saturates onto its ends, so an end the carrier cannot hold raises rather than warns. In binary32 (binary64):

  • at most 24 (53) magnitude bits, and as many in all with prng_bits;

  • both ends inside the carrier’s range. In two’s complement the end farther out is the bottom, \(-2^{\,n-\text{fl}}\), so \(n - \text{fl} \le 127\) (1023); a symmetric or unsigned format may reach one binade higher, \(n - 1 - \text{fl} \le 127\) (1023);

  • a largest value at or above the carrier’s smallest normal, \(2^{-126}\) (\(2^{-1022}\)), or nothing but zero is returned;

  • a step of at least \(2^{-125}\) (\(2^{-1021}\)), the floor of BinaryK’s subnormals, which a fixed-point grid is placed on the same way. A finer step warns: values near zero may round incorrectly.

A float16 or bfloat16 result is rounded once more when it is stored, and held to the rule for an elementwise result (What a narrower tensor can store): the inputs are already the dtype’s values, so only an end of the range can miss its grid. An end past the dtype’s largest value warns, as does a largest value that is not one of the dtype’s (a saturated result is then rounded again), and a largest value below the dtype’s smallest raises. There is no fixed-point matrix product, so there is no rule for one.

A FixedPoint can also be the element of a block format, which gives block floating point (Block floating point).

Block formats#

BinaryK and SuperFP give every element an exponent of its own. A block format shares one scale among a block of consecutive elements and stores the elements as narrow codes, so a 4-bit element can carry values over the whole range of a float32 tensor, one block at a time. The OCP Microscaling (MX) formats and NVIDIA’s NVFP4 are block formats, and they are what the newest accelerators multiply natively. The MX formats are defined by the OCP Microscaling Formats (MX) Specification (version 1.0, September 2023) and evaluated by Rouhani et al.; NVFP4 is described in Pretraining Large Language Models with NVFP4 (Section 2 and Appendix B).

A BlockFormat is defined by an element format, a scale format and a block size. The element is a BinaryK, a SuperFP or a FixedPoint, and the scale a BinaryK or a SuperFP (see SuperFP elements and scales and Block floating point, below). A tensor is split into blocks of block_size consecutive elements along one axis, its packed axis, and each block stores one scale code beside its element codes. Element \(i\) of block \(\kappa\) stands for the value

\[x_i \;\approx\; e_i\, \sigma_\kappa ,\]

its element value \(e_i\) times its block’s scale \(\sigma_\kappa\).

As an example, in the MX formats the scale format is E8M0, an unsigned exponent with no mantissa: code \(c\) is the power of two \(2^{c - 127}\), and code 255 is NaN. Writing \(X_\kappa\) for the block’s exponent,

\[\sigma_\kappa = 2^{X_\kappa}, \qquad -127 \le X_\kappa \le 127 ,\]

so the block scale alone places a block anywhere in float32’s range, and the format needs nothing else.

Tensor scales#

A scale format with a mantissa – NVFP4’s E4M3, or a SuperFP – follows a block’s largest magnitude more closely than a power of two can, but over a much shorter range: E4M3’s positive values run from \(2^{-9}\) to \(448\). By itself it could represent only a block whose largest magnitude is between \(2^{-9}\) and \(448\) times the element format’s largest value. Such a format can therefore use a second scale, one float32 number \(S_t\) for the whole tensor. This tensor scale can usually bring back the tensor into the scale format’s range, with the block scale differentiating the blocks:

\[\sigma_\kappa = s_\kappa\, S_t ,\]

where \(s_\kappa\) is the value of the block’s scale code and the product is computed in float32. \(S_t\) is one number for the whole tensor, kept beside the codes (the tensor_scale of a BlockPacked), so it adds nothing to the bytes per element. How a block is quantized gives its default value.

MPTorch currently pairs the tensor scale to the kind of block scale being used; it is not an option of its own. A BlockFormat therefore can be in one of three states:

  • Block scale only: a power-of-two scale, as in the MX presets. Such a format has no tensor scale, and passing tensor_scale= to it raises.

  • Block scale and tensor scale: any scale with a mantissa, as in NVFP4. A static tensor_scale=1.0 leaves the block scale alone, which is block scaling with a mantissa scale.

  • No scale: scale=None stores the element codes as they are.

A tensor scale without block scales is not available.

How a block is quantized#

A block format stores each element \(x_i\) of a block as an element value \(e_i\), next to one scale \(s\) for the whole block, so that

\[x_i \approx e_i\, s .\]

Quantizing a block means choosing both. The scale \(s\) has to be a value of the scale format, and each \(e_i\) a value of the element format. Once the scale is fixed the elements follow: \(e_i\) is \(x_i / s\) rounded to the element format, and the block then stands for the decoded values \(\hat{x}_i = e_i\, s\). The main question is which scale to take, and the answer depends on the format. A tensor is quantized one block at a time.

The scale a block asks for#

One scale serves the whole block, so it can put at least one element exactly where we want it, and the natural choice is the largest. Let \(a = \max_i |x_i|\) be the block’s largest magnitude (NaNs aside) and elem_max the element format’s largest value: 6 for E2M1, whose magnitudes are 0, 0.5, 1, 1.5, 2, 3, 4 and 6, and 448 for E4M3. An element above elem_max cannot be stored, so the codes are used best when the block’s largest element sits exactly at the top, \(a = \mathrm{elem\_max} \cdot s\). That gives the scale

\[r = \frac{a}{\mathrm{elem\_max}} .\]

But \(r\) is rarely a value of the scale format. Let \(\lfloor r \rfloor\) and \(\lceil r \rceil\) be the scale format’s values nearest to \(r\) from below and from above; for E8M0 these are the two powers of two around \(r\). They are the two most common candidates, and each has a cost:

  • \(s = \lfloor r \rfloor\) is too small. The block’s largest element lands at \(a / \lfloor r \rfloor = \mathrm{elem\_max} \cdot r / \lfloor r \rfloor\), above elem_max. No code holds such a value, so it is clipped to elem_max (it saturates), in every rounding mode, and decodes as

    \[\hat{a} \;=\; \mathrm{elem\_max} \cdot \lfloor r \rfloor \;=\; a \cdot \frac{\lfloor r \rfloor}{r} \;<\; a .\]

    The block’s largest value comes back too small by the factor \(\lfloor r \rfloor / r\).

  • \(s = \lceil r \rceil\) is too large. The block’s largest element lands at \(\mathrm{elem\_max} \cdot r / \lceil r \rceil\), below elem_max, so every element is in range. But two neighbouring decoded values are one element step \(\delta\) times the scale apart, and that distance is now

    \[\delta \cdot \lceil r \rceil \;>\; \delta \cdot r .\]

    The block’s grid is coarser than necessary by the factor \(\lceil r \rceil / r\). Every element is rounded more coarsely, and small values reach zero sooner: rounded to nearest, an element becomes zero once its magnitude is below half the element format’s smallest value times the scale, \(0.25\, \lceil r \rceil\) for E2M1.

The run at the end of this section shows both choices on one MXFP4 block whose largest magnitude is 3.8. It asks for \(r = 3.8 / 6 \approx 0.63\), so \(\lfloor r \rfloor = 1/2\) and \(\lceil r \rceil = 1\):

  • Under the scale 1/2, 3.8 is 7.6 in the element’s units. It is clipped to 6 and decodes as \(6 \cdot 1/2 = 3.0\), which is 21% low: \(\lfloor r \rfloor / r = 0.5 / 0.63 = 0.79\).

  • Under the scale 1, it is 3.8, rounds to 4 and decodes as 4.0, which is 5% high. But the grid is twice as coarse: the block’s 0.3 decodes as 0.5 instead of 0.25, and anything below 0.25 would decode as zero.

The four rules: one dividing line each#

A block gets one scale, chosen once from the block’s own values and stored with it. A rule makes this choice: given a block, it returns the lower candidate or the upper one. Blocks hold different values, so the same rule gives some blocks of a tensor the lower candidate and others the upper one.

BlockFormat(..., scale_rounding=) names the rule, a member of ScaleRounding. Four of the rules choose between the two candidates and are described here; the other three also consider a third scale option (see Four Over Six, below).

A rule’s answer depends on where the scale the block asks for, \(r\), lies between the block’s two candidates:

\[\rho = \frac{r}{\lfloor r \rfloor} .\]

Under the lower candidate the block’s largest element lands at \(\mathrm{elem\_max} \cdot \rho\), so \(\rho\) also measures how much that candidate clips:

  • \(\rho = 1\): the lower candidate is the scale the block asks for, and nothing is clipped.

  • A larger \(\rho\): the lower candidate clips more, and the case for the upper one is stronger. Between two powers of two, \(\rho\) is below 2.

Each of the four rules has a dividing line \(\theta\), and gives a block

  • the lower candidate, \(\lfloor r \rfloor\), if the block’s \(\rho\) is below the line: there is little to clip, so the block keeps the finer grid;

  • the upper candidate, \(\lceil r \rceil\), if the block’s \(\rho\) is above the line: too much would be clipped, so the block takes the coarser grid instead.

A rule with a low line gives most blocks the upper candidate: it clips little, and many blocks get the coarser grid. A rule with a high line does the reverse. The earlier example block (largest magnitude 3.8) has \(\rho = 0.63 / 0.5 = 1.27\), above the lines of UP and SELECTIVE and below those of OCP and NEAREST. The first two give it the scale 1 and the other two the scale 1/2, as the run shows.

OCP

This rule never computes \(r\). It rounds \(a\) and elem_max each down to a power of two, and divides:

\[s = 2^{\lfloor \log_2 a \rfloor - e_{\max}}, \qquad e_{\max} = \lfloor \log_2(\mathrm{elem\_max}) \rfloor .\]

This is the conversion that the OCP Microscaling Formats (MX) Specification gives (version 1.0, Section 6.3). It needs only the exponent of \(a\), and no division. The result is still one of the two candidates: the power of two that puts the block’s largest element in the element format’s top binade, \([2^{e_{\max}}, 2^{e_{\max}+1})\). For E2M1 that binade is \([4, 8)\), but E2M1 stops at 6. The rule therefore takes \(\lfloor r \rfloor\) whenever the largest element then stays below 8, and that element is clipped if it is above 6, by up to a quarter of its value. In general the dividing line is \(2^{e_{\max}+1} / \mathrm{elem\_max}\): 4/3 for E2M1 and 8/7 for E4M3. The rule exists for a power-of-two scale only.

NEAREST

Take the candidate nearer to \(r\), ties to even. This is NVFP4’s rule: Pretraining Large Language Models with NVFP4 (Appendix B.2) rounds each block’s scale to E4M3 this way. How much it clips depends on how far apart the two candidates are. In E4M3’s normal range they differ by at most a factor of 1.125, so the scale is at most a factor of 1.0625 below \(r\). The largest element then lands between 5.65 and 6.375, and E2M1 takes it to 6 either way. Two powers of two differ by a factor of 2: the dividing line is at 3/2, and the largest element is clipped by up to a third.

UP

Always take \(\lceil r \rceil\). No element ever passes elem_max. This is the rule that NVIDIA’s Recipes for Pre-training LLMs with MXFP8 (Section 3.3, Algorithm 1) uses for E8M0. Its authors describe the specification’s rule as rounding the scale down. They report training issues under it, which they hypothesize come from the clipped values, and none once the scale is rounded up. The price is the other cost, for every block: from a power of two, a grid up to twice as coarse as the block needs. The NVFP4 paper (Appendix B.4) counts this for a 4-bit element: in the worst case no element of the block reaches the values 4 and 6, and the block uses 2.58 of E2M1’s 3.58 binades. UP pays this even when the block’s largest element would have landed between 6 and 7 under \(\lfloor r \rfloor\), and so rounded to 6 without being clipped.

SELECTIVE

Take what NEAREST takes, except for blocks that the lower candidate would really clip; those get the upper one. Clipping does not always lose something. If E2M1’s values went on past 6, the next one would be 8. An element that lands between 6 and 7 would then still round to 6, so clipping it to 6 is no worse than rounding it. An element above 7 would round to 8, which does not exist, and clipping it to 6 moves it further than any rounding would.

The rule therefore uses a threshold \(T\): elem_max plus half the element format’s step above it (7 for E2M1). If the block’s largest element lands at or below \(T\) under NEAREST’s choice, the rule keeps that choice. Otherwise it takes \(\lceil r \rceil\). From a power of two its dividing line is \(T / \mathrm{elem\_max}\), which is 7/6 for E2M1. In the run, the block with 3.8 lands on 7.6 under the scale 1/2 and gets the scale 1, while the block with 3.3 lands on 6.6 and keeps the scale 1/2. This rule comes from no specification; it is MPTorch’s combination of the two before it.

Every rule’s result is kept within the scale format’s codes, and a block of zeros takes the smallest scale (code 0 for E8M0).

A rule need not stay between the two candidates. The three Four Over Six rules below may take a scale about 1.5 times \(r\).

By default scale_rounding is the rule of the scale format’s own specification: OCP for a power of two and NEAREST for a BinaryK with a mantissa. A SuperFP scale defaults to SELECTIVE, because its values below its normal binades are powers of two, where rounding to nearest clips the most (see SuperFP elements and scales). The format’s scale_rule is the rule in effect, and formats compare by it.

Scales with a mantissa, and the tensor scale#

A scale format with a mantissa (NVFP4’s E4M3, or a SuperFP) comes with a tensor scale \(S_t\) (see Tensor scales). An element is then stored as \(x_i \approx e_i\, s\, S_t\), and the scale the block asks for is measured relative to \(S_t\):

\[r = \frac{a}{\mathrm{elem\_max} \cdot S_t} .\]

The rules above choose between its two neighbours in the scale format, \(\lfloor r \rfloor\) and \(\lceil r \rceil\), as before. The chosen \(s\) stays inside the scale format: at most its largest value (448 for E4M3) and at least its smallest positive one. The block’s scale is the float32 product \(s \cdot S_t\).

By default \(S_t\) is computed from the tensor \(x\) itself:

\[S_t = \frac{\max|x|}{\mathrm{elem\_max} \cdot \mathrm{scale\_max}} ,\]

where scale_max is the scale format’s largest value, so \(S_t = \max|x| / (6 \cdot 448)\) for NVFP4. The block that holds the tensor’s largest magnitude then asks for exactly scale_max. It takes the largest scale and every other block a smaller one, so the scale format’s whole range lies below the tensor’s largest block. This is the NVFP4 paper’s choice (Appendix B.1 writes its reciprocal, the “global encode scale” \(6 \cdot 448 / \max|x|\)). Passing tensor_scale= gives a fixed value instead.

That range is finite. A block gets a scale of its own only while the scale it asks for is at least the scale format’s smallest positive value, \(s_{\min}\):

\[r \ge s_{\min} \quad\Longleftrightarrow\quad a \;\ge\; \mathrm{elem\_max} \cdot s_{\min} \cdot S_t \;=\; \max|x| \cdot \frac{s_{\min}}{\mathrm{scale\_max}} ,\]

where the last step uses the default \(S_t\). For E4M3, \(s_{\min} = 2^{-9}\) and scale_max is 448, so a block’s largest magnitude may be up to \(448 \cdot 2^{9} \approx 2.3 \cdot 10^{5}\) times smaller than the tensor’s. A block smaller than that still takes \(s_{\min}\). Its largest element then lands at \(\mathrm{elem\_max} \cdot r / s_{\min}\), below elem_max, and its elements are rounded coarsely or to zero.

With a mantissa the choice of rule matters less than with a power of two, because the two candidates are close together. In E4M3’s normal range, when NEAREST takes \(\lfloor r \rfloor\) it is at most a factor of 1.0625 below \(r\). E2M1’s top step (4 to 6) absorbs that, so SELECTIVE leaves NVFP4’s scales alone there. An element format with a finer top step (E2M3, E4M3) is clipped by that factor, and SELECTIVE gives those blocks \(\lceil r \rceil\) instead.

Four Over Six#

The rules so far all aim the block’s largest element at elem_max and choose the scale from the block’s largest magnitude alone. Four Over Six (Cook et al.) questions that aim. E2M1’s largest values are 3, 4 and 6. In a block whose largest element sits on 6, nothing between 67% and 100% of that element can be represented, and an element near 5 is off by a sixth of the block’s largest value after rounding. The paper finds that these near-maximal elements account for most of NVFP4’s quantization error (its Section 2.2). If the block’s largest element sits on 4 instead, the block gives up the value 6 but gains 3 at 75% of its largest value, and its other values are spaced more evenly.

A block therefore has a third candidate scale, and the rule chooses per block between two of the three:

  • the scale NEAREST takes, the candidate nearer to \(r\), under which the block’s largest element lands on elem_max (6 for E2M1);

  • the scale nearest to \(1.5\, r\), under which it lands on 4. In general the factor is elem_max over the largest power of two not above it, so 1.875 for E2M3 (7.5 and 4).

The rule quantizes the block under both scales in the call’s rounding mode, decodes both results, and measures each one’s error against the block’s original values. Let \(\hat{x}^{(6)}_i\) and \(\hat{x}^{(4)}_i\) be the decoded values under the first and the second scale, and \(E^{(6)}\), \(E^{(4)}\) their errors. The block takes the second scale if

\[E^{(4)} < E^{(6)} ,\]

and keeps the first otherwise, including on a tie. There are three rules, one per error measure, and the paper reports which worked best where:

FOUR_OVER_SIX_MSE

The sum of squared errors, \(E^{(k)} = \sum_i \big(\hat{x}^{(k)}_i - x_i\big)^2\). Best in most of the paper’s post-training quantization experiments (its Section 3.1).

FOUR_OVER_SIX_MAE

The sum of absolute errors, \(E^{(k)} = \sum_i \big|\hat{x}^{(k)}_i - x_i\big|\). Better than MSE in its pre-training experiments (its Appendix A.1).

FOUR_OVER_SIX_ABS_MAX

The largest absolute error of the block, \(E^{(k)} = \max_i \big|\hat{x}^{(k)}_i - x_i\big|\).

In the paper’s example (its Table 2, and the run below), the block \([10, 20, 30, 40]\) has the scale 6.5 under NEAREST and decodes as \([9.75, 19.5, 26, 39]\). Its second candidate is the scale 10, under which it is exact, so every measure takes it.

Four things are specific to these rules:

  • The scale format needs a mantissa. E4M3 can hold two scales a factor of 1.5 apart and E8M0 cannot, so a Four Over Six rule on a power-of-two scale raises. The paper has the same limit: the method does not apply to MXFP4 (its Section 5.2).

  • The default tensor scale changes. It gives the tensor’s largest block the scale 256 instead of 448, so that this block also has a second candidate: 256 is the largest scale whose multiple by 1.5 is still an E4M3 value (384). This follows the paper’s Appendix A.2. The format’s top_scale is that scale.

  • Errors are counted in fixed point. In the sums above, each \(|\hat{x}^{(k)}_i - x_i|\) is first truncated to a multiple of \(2^{\lfloor \log_2 a \rfloor - 22}\), at most a four millionth of the block’s largest magnitude, and the measure is added up in integers. A block’s error is then exact. The CPU and a GPU add the elements up in different orders, and with exact errors they always choose the same scale; with a sum of floats they could differ at a near tie.

  • Stochastic rounding uses one draw per element. Under SR both candidates round an element with the same random draw, the one the element is stored with. The choice is made on the rounded values, as in the paper. The paper notes that this favours the smaller error and so reintroduces a bias (its Appendix A.3).

The rule rounds every element a second time in each block whose two scales differ. On a CPU, block_quantize takes about 2.2 times as long as under NEAREST. For pre-training the paper recommends the rule for activations only (its Appendix A.4).

With 2D tiles (below) the block is the whole tile. The tile has one pair of candidate scales, from its largest magnitude; the error is taken over all of its elements; and it makes one choice. The paper’s reference implementation does the same for 16 x 16 tiles (its block_scale_2d). Since the errors are integers, the choice does not depend on the order in which they are added up, and a square tile makes the same choice whichever axis the tensor is packed along.

Rounding the elements#

Each element is divided by its block’s scale. The division is exact for a power of two and is done in float32 for a scale with a mantissa. The quotient is rounded by the element format’s cast (a BinaryK’s or a SuperFP’s) in the call’s rounding mode, under SaturationMode.SAT_FINITE, and then clamped to elem_max. With \(Q\) for that cast and \(\sigma\) for the block’s scale (\(s\), or \(s\, S_t\) for a scale with a mantissa):

\[e_i = \operatorname{sign}(x_i) \cdot \min\!\big( |Q(x_i / \sigma)|,\ \mathrm{elem\_max} \big) .\]

Every value above elem_max lands on it, in every rounding mode. The rounding mode applies to the elements only; the rule for the scale never depends on it.

The clamp is where OCP’s element formats differ from P3109’s. As a P3109 format, E4M3 has the largest finite value 480, but OCP spends that code on NaN. MXFP8_E4M3 therefore has elem_max=448.0 and nan_code=0x7F.

Decoding, and the special values#

Decoding an element is one float32 product, its value times its block’s scale:

\[\hat{x}_i = e_i\, \sigma, \qquad \sigma = s \ \text{ for a power-of-two scale}, \quad \sigma = s\, S_t \ \text{ for a scale with a mantissa},\]

where \(s\, S_t\) is itself a float32 product, computed once per block. The product \(e_i\, \sigma\) is exact for every OCP format. Two rules hold for every block format:

  • Non-finite values. An infinity saturates to elem_max. With an E8M0 scale its block takes the largest scale, \(2^{127}\). Since \(448 \cdot 2^{127}\) is past binary32, the element decodes to an infinity again. A NaN takes the element’s NaN code when the format has one (E4M3, E5M2). Otherwise the block’s scale becomes the scale’s NaN and the whole block decodes to NaN; for a 2D tile (below) that is up to 16,384 elements. With neither a NaN code nor a scale, a NaN becomes elem_max and is lost. The OCP specification leaves the conversion of a NaN to the implementation for the formats without a NaN code (Sections 5.3.2 and 5.3.3); these are MPTorch’s choices.

  • One zero. An element code with only its sign bit set is OCP’s \(-0\). MPTorch never writes it and reads it as \(+0\), so no block op returns -0.0, like every other cast in the library.

Quantizing twice#

Quantizing an already quantized tensor does not always return it unchanged, because the second pass chooses its scales from the rounded values:

  • With a power-of-two scale, OCP, UP and SELECTIVE change nothing the second time.

  • NEAREST with a power-of-two scale can move values. If the largest element was rounded down, the block now asks for a smaller scale, which can round to the next power of two down. Under that scale the element saturates.

  • UP with a mantissa scale can also move values, and so can any rule with a mantissa scale when the element format is finer than E2M1.

  • A Four Over Six rule changes nothing the second time on NVFP4. A block comes back with its largest element on the value its scale was chosen for, and under that scale it has no error at all.

SuperFP elements and scales#

A SuperFP element or scale spends the codes that a binaryK spends on subnormals, and more, on powers of two below its normal binades: the supernormals.

  • As a block element, it trades the uniform steps near the top of a block for reach at the bottom. Small elements of a block with a wide spread survive where E2M1 flushes them to zero.

  • As a scale, it reaches far below E4M3’s \(2^{-9}\) in the same byte.

Its codes follow the format’s own layout: zero, then the supernormals from code 1, then the normal binades as in a binaryK. It rounds by the superfp casts, so a tie between two supernormals goes to the power of two with an even exponent, as in superfp_quantize(). A superfp scale is cast like E4M3 and multiplied by a tensor scale, and its all-ones code is NaN. Its default rule is ScaleRounding.SELECTIVE, because below its normal binades a superfp scale holds only powers of two, and rounding such a scale to nearest can clip a block’s largest element by up to a third. The paragraph after the run gives the details.

    codes, torch.tensor([[127]], dtype=torch.uint8), sfp4, (1, 32), 1, 1.0, torch.float32
)

Rounding a scale to nearest costs more here. Below its normal binades a superfp scale holds only powers of two, so the nearest scale can be a factor of 1.5 below \(a / \mathrm{elem\_max}\). Take a block whose ratio is 0.35:

  • Under NEAREST it gets the scale 0.25. Its largest element is 8.4 in E2M1’s units, saturates to 6, and decodes 29% low (33% at worst).

Block floating point#

A FixedPoint element gives block floating point: integer elements that share an exponent. bfp() builds the usual shape, FixedPoint(bits, bits - 2, symmetric=True) elements with an E8M0 scale. An element has a sign and bits - 1 magnitude bits, one step of \(2^{-(\text{bits} - 2)}\) from zero to its largest value, \(2 - 2^{-(\text{bits} - 2)}\). So emax is 0, and OCP’s rule gives a block the scale \(2^{\lfloor \log_2 a \rfloor}\) for its largest magnitude \(a\).

  • Signed and symmetric only. A block code is sign-magnitude. It has no code for a two’s complement format’s bottom, \(-2^{\,n-\text{fl}}\), and an unsigned element would lose its top code. Both raise. Any other fl gives the same block values and only moves emax, and any scale works, a cast one such as E4M3 included.

  • One grid. The kernels decode and round the element as the binaryK layout its integer code is: one exponent bit, \(n - 1\) mantissa bits and bias \(2 - n + \text{fl}\), whose exponent field 0 holds the codes below \(2^{n-1}\) and field 1 the rest, one step apart. No kernel has a fixed-point arm. A quantized block is therefore fixedpoint_quantize() of each element over the block’s scale, times that scale, in every deterministic mode, as the run shows.

  • Stochastic rounding goes through binaryK’s cast on that layout. It is exact on the upper half of the element’s range (field 1, rounded on the word). On the lower half (field 0, binaryK’s SUBNORMALS arm) it adds a power of two in the carrier first, so a probability can be one step of \(2^{-N}\) off just under a level (Stochastic rounding). fixedpoint_quantize() itself is exact.

  • The block GEMM takes element codes of up to 8 bits, so bfp(2) to bfp(8), paired with any block format. bfp(9) to bfp(16) pack, unpack and quantize only.

  • The carrier holds the element to the fixed-point rule (FixedPoint: one step across the range), its stochastic-rounding bits included.

2D tiles#

With block_rows > 1 a scale is shared by a tile of block_rows rows of block_size elements. The rows run along the axis before the packed one, never across a batch dimension. A tile changes only where the scale comes from: the codes and their layout are the 1D format’s, and scales has one row per tile. Two examples:

  • dataclasses.replace(NVFP4, block_rows=16) is NVFP4 with 16 x 16 tiles, the weight format of NVIDIA’s NVFP4 pretraining recipe (which scales activations and gradients 1 x 16).

  • 128 x 128 tiles are DeepSeek-V3’s weight blocking, here with an E8M0 scale (a scale is one byte).

A square tile covers the same elements whichever of a matrix’s two axes is packed, so it quantizes the matrix to the same values either way, in every deterministic rounding mode and under every scale rule, the Four Over Six rules included. One packed weight can therefore serve both a layer’s forward pass and its input gradient, which reads the weight transposed. A 1D block runs along one axis only and quantizes the two orientations differently. A matrix product needs its operands blocked along the dimension it sums over, because only then can each block’s scales be factored out of that block’s part of the sum, which is how block-format hardware computes it (see Block matrix products, “Why the blocks run along K”).

Stochastic rounding#

Under SR the rounding direction is random, with a probability that depends on where \(x\) sits between its two neighbours. Let \(f = (x - \lfloor x \rfloor_F) / (\lceil x \rceil_F - \lfloor x \rfloor_F) \in [0, 1)\) be that fraction. The ideal rule is \(\Pr(\text{up}) = f\), which makes the rounding unbiased: \(\mathbb{E}[Q(x)] = x\).

P3109 defines three stochastic modes, which read \(N\) random bits (prng_bits) three ways. Let \(\eta\) be the fraction of \(|x|\) between its two neighbours (\(\eta = f\) when \(x > 0\)), \(R\) a uniform integer in \([0, 2^N)\) and \(X = \eta 2^N\). The magnitude rounds away from zero when:

mode

P3109

rounds away iff

\(\Pr(\text{away})\)

SR (SR_A)

StochasticA

\(\lfloor X \rfloor + R \ge 2^N\)

\(\lfloor X \rfloor / 2^N\)

SR_B

StochasticB

\(\lfloor 2X \rfloor + 2R + 1 \ge 2^{N+1}\)

\(\lfloor X + 1/2 \rfloor / 2^N\)

SR_C

StochasticC

\(\mathrm{RNITE}(X) + R \ge 2^N\)

\(\mathrm{RNITE}(X) / 2^N\)

RNITE rounds to the nearest integer, ties to even. Each mode quantizes the ideal probability \(\eta\) to steps of \(2^{-N}\). StochasticA truncates it, which biases a value toward zero by less than one step. StochasticB and C round it to nearest, so they are off by at most half a step either way; they differ only at an exact half. All three tend to \(\eta\) as \(N\) grows.

prng_bits is set on the format (BinaryK(8, 4, prng_bits=8)) and is ignored by the deterministic modes. Three consequences of the definitions:

  • With prng_bits=0 nothing is random. SR is RZ, SR_B is RNA, and SR_C rounds to nearest with ties toward zero. The SR row above comes from a format with no random bits and is identical to the RZ row.

  • The format’s mantissa plus its random bits must fit in the carrier’s mantissa: 23 bits in binary32, 52 in binary64. Each call checks this. A FixedPoint format’s magnitude bits plus its random bits must fit the carrier’s precision, 24 bits or 53. At that bound the carrier holds no bit below the random ones, and SR_B and SR_C are SR.

  • The definition holds in every region of every format, with the region’s own two neighbours:

    • a BinaryK’s normal binades and its subnormals;

    • the floor of NORMALS and EXTENDED_NORMALS, between zero and the smallest value;

    • a SuperFP’s supernormal binades, and the region below its smallest value;

    • FixedPoint everywhere.

    The casts compute it on the input’s word with integers, so nothing is rounded in the carrier first, and the random bits are the same \(N\) bits everywhere.

  • One exception, in formats that already warn that the carrier cannot place their bottom. In a SuperFP whose smallest value is itself a carrier subnormal, and in a P = 1 format whose floor is \(2^{-126}\) (\(2^{-1022}\)) and whose random bits fill the carrier’s mantissa, the floor’s draw step can be finer than the carrier’s subnormal spacing. A carrier subnormal below the floor then always rounds up to it, where the definition would round up with probability \(|x| / x_{\min}\). Inputs at or above the floor are unaffected. Computing the exact probability there cost the CUDA stochastic GEMMs 6–8% for every format, so the casts do not.

A float64 operand is rounded in binary64, and its bits are drawn there too, two random words per draw.

The random streams are seeded from PyTorch’s default generator, so torch.manual_seed makes a stochastic run reproducible. In a GEMM each output element has its own stream, keyed on its position, so the result does not depend on how the work is split across threads.

Carriers#

Every operation is computed in a carrier, an IEEE binary float with far more precision and range than the format it simulates. There are two carriers, binary32 and binary64, and by default a tensor’s dtype picks one:

  • A float32, float16 or bfloat16 tensor is computed in binary32. A float16 or bfloat16 result is then stored back in its own dtype, which is a second rounding (see What a narrower tensor can store).

  • A float64 tensor is computed in binary64 throughout. An elementwise quantizer rounds each value once, directly. A matrix product computes every partial product and every running sum in binary64 before rounding it.

Moving a model to float64 therefore does more than widen its storage:

  • Formats that binary32 cannot hold become simulable: up to 53 bits of precision, ten exponent bits, values down to \(2^{-1021}\).

  • A value that binary32 cannot hold is rounded on its own bits, not on the nearest float32.

The two carriers agree wherever both hold every intermediate exactly. Rounding a float64 tensor of float32 values to a format binary32 holds gives exactly the float32 answer. So does a matrix product whose every product and sum is exact in binary32, which is usual once a quantizer has rounded its operands to a narrow format.

Every function and object that computes takes a carrier keyword to override the default. Its value is the torch.dtype whose arithmetic the carrier uses: torch.float64 for binary64, torch.float32 for binary32, and None (the default) for the tensor’s own.

carrier=torch.float64 gives a float32, float16 or bfloat16 tensor binary64’s arithmetic. Its operands are widened to float64, computed and rounded in binary64, and the result is narrowed back to the tensor’s dtype with a single rounding. This is bit for bit the float64 call on the widened tensor, then stored. The result keeps the tensor’s dtype either way.

A carrier is never narrower than its tensor, so carrier=torch.float32 on a float64 tensor raises: narrowing the operands would round every input once before the format does.

The keyword is taken by the quantizers (binaryK_quantize(), superfp_quantize(), Quant), the matrix products (SplitMac, FusedMac and the flat *_matmul functions) and the layer factories (binaryK_gemm_formats() and its siblings).

(*) NORMALS and EXTENDED_NORMALS. The bound is one binade higher (\(2^{-125}\) and \(2^{-1021}\)) at \(P = 1\), and for EXTENDED_NORMALS at the carrier’s full precision, \(P = 24\) and \(P = 53\).

The last row is a cost worth knowing. On a GPU, binary64 arithmetic is several times slower than binary32, so a float64 model’s matrix products are too (on the CPU the two are within a few percent). A narrower tensor that names binary64 pays that cost, plus a float64 copy of each operand and a narrowed copy of the result. In the other direction the choice is one of dtype, not of carrier: a float64 model that needs only formats binary32 can carry gets binary32’s speed by being a float32 model.

The rest of this section derives the table’s bounds and says what happens to a format that exceeds them.

What the carrier can hold#

The carrier has “far more” precision and range than every format in this guide, but not than every possible format. The carrier sets a bound on the format’s parameters. A format outside that bound is quantized partially: the result is still a tensor of plausible numbers, but some of the format’s values never appear in it. There are three limits, stated here in the format’s own terms, with binary64’s in parentheses:

  • Precision. \(P \le 24\) (53) for BinaryK, man_bits <= 23 (52) for SuperFP, and at most 24 (53) magnitude bits for FixedPoint. These are the carrier’s significand bits; it cannot hold a finer grid.

  • The top. The largest finite value must be at most the carrier’s. That is \(\text{bias} \ge 2^E - 128\) (\(2^E - 1024\)), where \(E\) is the exponent width (exp_bits for a SuperFP). Above that the cast saturates at the carrier’s largest value on the format’s grid, and the codes above it are unreachable. A FixedPoint format’s ends are its saturation points, so both must be carrier values (FixedPoint: one step across the range).

  • The bottom. A subnormal carrier value has exponent field 0 whatever its magnitude. Any part of a cast that reads that field therefore cannot tell values apart below the carrier’s smallest normal, \(2^{-126}\) (\(2^{-1022}\)). The limit depends on which parts of the cast read it:

    • BinaryK’s subnormals and SuperFP’s supernormals are placed on their grid using that field. Their smallest value must be at least \(2^{-125}\) (\(2^{-1021}\)), one binade above the carrier’s smallest normal. That is \(\text{bias} + P \le 127\) (1023) for BinaryK, and \(e_{\max} - b + 2 - n \ge -125\) (\(-1021\)) for SuperFP (using the notations from SuperFP: precision at the top, range below).

    • The two non-P3109 subnormal modes, NORMALS and EXTENDED_NORMALS, find their bottom by comparing the input’s magnitude with the format’s smallest value \(x_{\min}\), which reads no field. They are exact as long as \(x_{\min}\) is at least the carrier’s smallest normal. Below that, \(x_{\min}\) is not a normal carrier value and nothing is flushed to zero at all.

    • In two cases \(x_{\min}\) must be one binade higher, at least \(2^{-125}\) (\(2^{-1021}\)). Under rounding to nearest, the comparison also needs the midpoint \(x_{\min} / 2\) between zero and \(x_{\min}\), and in these two cases the carrier cannot place it:

      • At \(P = 1\). The format has one value per binade, and the rounding before the comparison works on the exponent field. With \(x_{\min} = 2^{-126}\), the midpoint \(2^{-127}\) (\(2^{-1023}\)) is a carrier subnormal, in the exponent field that all subnormals share. The rounding reads it as a tie between two binades and returns \(x_{\min}\), where round-to-nearest-even should return zero.

      • An EXTENDED_NORMALS format at the carrier’s full precision, \(P = 24\) (53). With its lowest binade starting at \(2^{-126}\), its smallest value is \(x_{\min} = 2^{-126}\,(1 + 2^{-23})\). The midpoint, \(2^{-127}\,(1 + 2^{-23})\), needs a step of \(2^{-150}\) (\(2^{-1075}\)), which is finer than the carrier’s finest step, \(2^{-149}\) (\(2^{-1074}\)). The carrier holds \(2^{-127}\) in its place. An input of exactly \(2^{-127}\) is below the true midpoint and should round to zero, but it now looks like a tie, and round-to-nearest-away returns \(x_{\min}\).

The last two limits together mean that a simulated format may span at most 253 binades (2045). So seven exponent bits is the most either family can carry in binary32, and ten in binary64. At P3109’s default bias that is \(K - P \le 7\) (10) for a signed BinaryK and \(K - P \le 6\) (9) for an unsigned one.

The 8-bit and 6-bit formats of this guide are well inside binary32’s bounds. A format with eight exponent bits is not, whatever its bias:

  • Binary16p8 and Binary32p24 reach below binary32’s floor. The kernel pages use Binary16p8 as an accumulator and silence the warning described below.

  • The bfloat16 and float32 layouts also reach past its top.

binary64 holds all four.

The carrier depends on the tensor, not on the format, so the limits are checked on every call, against the carrier that the call rounds in. The quantizers of Quantizers, the kernels of Quantized numerical kernels and the layers built on them all do this. When a BinaryK or SuperFP is built, it checks only what neither carrier can do. The plain-integer wrappers never see a format object, and check the same thing when they resolve their format. There is one rule for both, so binaryK_matmul(a, b, mul_K=16, mul_P=8) reports what qmatmul(a, b, BinaryK(16, 8)) reports.

There are two severities. What separates them is whether the format still works, not which limit it misses:

  • A format whose range exceeds the carrier’s warns with FormatRangeWarning, naming the line that made the call. This covers a format that reaches above the carrier’s largest finite value, is spaced finer than its smallest subnormal (\(2^{-149}\), \(2^{-1074}\)), or has a smallest value below the floor given in the list above. Such a format quantizes correctly over the part the carrier holds, and some of its values are never returned. A wide BinaryK used as a precision-only target is this case, so the warning can be silenced with warnings.simplefilter() when that is intended.

  • A format that cannot function raises ValueError. This covers more precision than the carrier’s, stochastic-rounding bits with no significand left to draw from, an exponent field wider than the kernels shift by, a SuperFP whose normal_binades leaves no supernormal codes, a FixedPoint end past the carrier’s largest value, and a format whose largest finite value is below the carrier’s normals, where every nonzero result overflows.

The run below shows both carriers on the same inputs and formats:

  • a float64 value rounded once in binary64, and the nearest float32 value rounded in binary32 and, with carrier=torch.float64, in binary64;

  • four formats, each checked against each carrier when a tensor meets it;

  • a 30-bit format computed exactly on a float64 tensor;

  • a product of float32 operands whose rounding only binary64 gets right.

"""Carriers: the float arithmetic a tensor is rounded in, and what each can hold."""

import math
import warnings

import torch

from mptorch import BinaryK, FormatRangeWarning
from mptorch.quant import Quant, SplitMac, qmatmul

F32, F64 = torch.float32, torch.float64

# The carrier is the tensor's unless a call names one: binary64 for float64,
# binary32 for the rest. 1.0625 is the tie between 1.0 and 1.125 on Binary8p4's
# grid, and 1.1875 the tie between 1.125 and 1.25; 2**-30 either side of them is
# a bit float32 does not have, so the float32 value *is* the tie, and
# round-to-nearest-even takes over -- in either carrier, since binary64 cannot
# give a float32 tensor back bits it never had.
x = torch.tensor([1.0625 + 2**-30, 1.1875 - 2**-30], dtype=F64)
binary8p4 = BinaryK(8, 4)
print("input                              ", x.tolist())
print("float64, rounded in binary64       ", Quant(binary8p4)(x).tolist())
print("float32, rounded in binary32       ", Quant(binary8p4)(x.float()).tolist())
print("float32, carrier=torch.float64     ", Quant(binary8p4, carrier=F64)(x.float()).tolist())

# What each carrier makes of a format is checked when a tensor meets it, not
# when the format is built: here by a float32 tensor in each carrier, and a
# float64 one.
formats = [
    BinaryK(8, 4),  # Binary8p4: well inside both
    BinaryK(16, 8),  # smallest value 2**-134, below binary32's floor
    BinaryK(40, 30),  # 30 bits of precision, ten exponent bits
    BinaryK(64, 53),  # eleven exponent bits: past binary64 at the bottom too
]
calls = {
    "float32": lambda fmt: Quant(fmt)(torch.ones(4)),
    "float32, carrier=torch.float64": lambda fmt: Quant(fmt, carrier=F64)(torch.ones(4)),
    "float64": lambda fmt: Quant(fmt)(torch.ones(4, dtype=F64)),
}
print()
for fmt in formats:
    print(f"BinaryK({fmt.K}, {fmt.P})")
    for name, call in calls.items():
        with warnings.catch_warnings(record=True) as caught:
            warnings.simplefilter("always", FormatRangeWarning)
            try:
                call(fmt)
                verdict = f"warns ({caught[0].message}" if caught else "ok"
            except ValueError as e:
                verdict = f"raises ({e}"
        print(f"  {name}: {verdict.split(': ')[0] + (')' if verdict != 'ok' else '')}")

# Only what no carrier can do raises when the format is built.
try:
    BinaryK(64, 54)
except ValueError as e:
    print("\nBinaryK(64, 54):", str(e).split(": ")[0])

# A format float32 cannot carry, exactly, on a float64 tensor: pi to 30 bits
# of precision is pi rounded to the nearest multiple of 2**-28.
pi = torch.tensor([math.pi], dtype=F64)
got = Quant(BinaryK(40, 30))(pi).item()
want = round(math.pi * 2**28) / 2**28
print(
    f"\npi in BinaryK(40, 30): {got!r}, round(pi * 2**28) / 2**28: {want!r}, equal: {got == want}"
)

# Where the carrier does move a float32 result: a product. (1 + 2**-13)**2 is
# 1 + 2**-12 + 2**-26, a hair above the tie between 1 and 1 + 2**-11 on a
# 12-bit grid. binary32 rounds the product to 24 bits first, onto the tie, and
# RNE takes it down; binary64 holds the hair and rounds up. The result is a
# float32 tensor either way.
one = torch.full((1, 1), 1 + 2**-13)
p12 = BinaryK(16, 12)
print()
for carrier in (None, F64):
    out = qmatmul(one, one, SplitMac(p12, p12, carrier=carrier))
    print(f"(1 + 2**-13)**2 in P=12, carrier={carrier}: {out.item()!r} ({out.dtype})")

# A carrier is never narrower than the tensor: rounding a float64 one in
# binary32 would round every input once before the format does.
try:
    Quant(binary8p4, carrier=F32)(x)
except ValueError as e:
    print("\ncarrier=torch.float32 on float64:", str(e).split(";")[0])

What a narrower tensor can store#

A float16 or bfloat16 tensor is rounded in binary32, its default carrier, and the result is converted back when it is stored. The same happens to a float32 tensor under carrier=torch.float64, whose result is rounded in binary64. That conversion is a second rounding, onto the dtype’s grid, and MPTorch rounds it correctly to nearest.

For a float64 result stored as float16 or bfloat16, MPTorch rounds once, directly from float64 onto the dtype’s grid. It does not use PyTorch’s .to(), which converts float64 to bfloat16, and on most platforms to float16, in two steps: first to float32, then to the dtype. Two roundings can give a different result from one. Take the float64 value \(1 + 2^{-8} + 2^{-30}\). It lies just above the midpoint of the bfloat16 values \(1\) and \(1 + 2^{-7}\), so it should become \(1 + 2^{-7}\). PyTorch’s first step rounds it to \(1 + 2^{-8}\), which is exactly the midpoint, and its second step then rounds that tie to \(1\).

A format whose results are not all values of the dtype is quantized partially, as in the previous section, with one difference: a result above the dtype’s largest finite value is stored as \(\pm\infty\) whatever the format’s saturation mode. A SAT_FINITE format overflows too.

The dtype depends on the tensor, not on the format, so this is checked on every call. The check is made against the format whose values the result holds, and the rule depends on what the call rounded.

A GEMM’s result is the output of its last rounding: the accumulate format of a SplitMac, or the fused format of a FusedMac. That rounding is applied to products and sums that can land anywhere, so every value of the format can occur as a result, and all of them must be values of the dtype. For a BinaryK:

A SuperFP is held to the same three bounds, in its own parameters. The rule does not depend on the carrier that rounded the result.

  • In binary32, only the precision bound is new for bfloat16. Its range is float32’s to within its precision, so a format that passes the float32 checks with at most eight bits of precision is inside it at both ends.

  • In binary64, the carrier accepts ranges that no narrower dtype holds, so every row of the table can apply.

A SplitMac’s multiply format is never stored, because its products are intermediates in the carrier. A step left unrounded stores no format’s values at all.

An elementwise quantizer’s result is the format’s rounding of a value that is already a value of the dtype. Wherever the format is at least as fine as the dtype, the result is the input itself. So neither high precision nor a fine bottom causes a problem; only the edges of the format’s range can land off the dtype’s grid. Each of these cases warns:

  • The format reaches past the dtype’s largest finite value, and that value is not on the format’s grid. An input near it then rounds up, out of the dtype’s range.

  • The format’s largest finite value is inside the dtype’s range but is not a value of the dtype, and the format saturates onto it.

  • An EXTENDED_NORMALS format’s hole, \(2^{-\text{bias}}\), is a value of the dtype, but the first value above it, where such an input rounds, is not.

Either kind of call raises for a format whose largest finite value is below the dtype’s smallest. Such a tensor could store nothing of the format but zero.

A block format’s decoded values are an element value times its block’s scale, computed in the carrier: binary64 for a float64 tensor or carrier=torch.float64, binary32 otherwise.

  • A BlockFormat’s element and cast scale must be formats the carrier holds entirely, and a power-of-two scale’s codes must lie in its range (\(2^{\pm 127}\) in binary32, \(2^{\pm 1023}\) in binary64). Building the format checks binary64’s bounds. A call that rounds in binary32 checks binary32’s, so an element with nine or ten exponent bits is a format of float64 tensors.

  • A packed tensor remembers the carrier it was packed in, and unpacking or multiplying it runs in that carrier or a wider one.

A result narrower than its carrier (float16 or bfloat16, and float32 too in binary64) rounds the decoded values a second time wherever the dtype does not hold them, and FormatRangeWarning reports it. That is always the case for a format with a tensor scale (NVFP4), whose decoded values are products in the carrier. For an E8M0 format it happens only when its largest element value has more significant bits than the dtype.

x = torch.ones(4, 4, dtype=torch.float16)
binaryK_quantize(x, 8, 4)                # fine
binaryK_quantize(x, 8, 3, bias=15)       # FormatRangeWarning: rounds up past 65504
binaryK_quantize(x, 16, 12, bias=8)      # fine: float16's values come back as they are
binaryK_matmul_fma(x, x, fma_K=16, fma_P=12, fma_bias=8)  # ValueError: 12 bits
qmatmul(x, x, SplitMac(BinaryK(8, 4), BinaryK(16, 11)))    # FormatRangeWarning: 2**-25

Both rules were measured against the kernels, not only derived. format_limits.py --dtype float16 --audit runs a format through a fused GEMM over operands of the dtype, and through the quantizer over every value of the dtype. sweep --dtype float16 --audit walks each boundary above. With --carrier binary64 both also go through the widened operands and the narrowed result.

On an Apple GPU#

On macOS every op also runs on "mps" tensors, as Metal kernels compiled from the same casts, GEMM policies, accumulate algorithms, convolution gathers and block-format decode that the CPU runs. MPS has no float64, so the carrier there is always binary32. float32, float16 and bfloat16 tensors compute exactly as on the CPU. carrier=torch.float64 and a float64 result are refused, because the device cannot hold a float64 tensor.

The results are the CPU’s, bit for bit, stochastic rounding included. An MPS call draws its one seed from the CPU generator, as a CPU call does, and gives every element the same random word. torch.manual_seed therefore reproduces a run across the two devices, not only on one. (CUDA draws from its own generator.)

The GPU’s float unit differs from the CPU’s in two ways. Both affect what a GEMM computes between its roundings, not the roundings themselves:

  • Subnormals. Apple GPUs flush binary32 subnormals to zero, in operands and results, in every mode Metal offers. The casts round on the word and are not affected. But a product, a running sum or a fused multiply-add whose exact value is below \(2^{-126}\) in magnitude becomes zero before the format sees it. The effect depends on the rounding mode:

    • Under RZ the CPU returns zero too.

    • Under RNE and RNA it does as well, for every format whose smallest value is at least \(2^{-125}\).

    • Under RU, RD, RO and SR the CPU can round such a value to the format’s smallest value where the GPU gives zero.

    • A sum left unrounded (accumulate_quant=False) can hold a subnormal on the CPU that the GPU drops.

    The same holds for the compensation of KAHAN, the block sums of BLOCK and TREE, and the products and sums of a block product. The quantizers are not affected, and neither are the block formats’ packing and decoding. They round every input exactly, subnormal ones included, in every mode. A decoded block value can itself be a subnormal (an E8M0 scale reaches \(2^{-127}\)), and it is the CPU’s, in a float32 and in a bfloat16 result.

  • NaN payloads. A NaN that reaches a product or a sum comes out of the GPU’s float unit as its canonical NaN, where the CPU keeps the operand’s payload. The casts pass a NaN through unchanged on every device, so a quantizer’s NaNs keep their payload.

The first call with a given format compiles its kernel, which takes from about 20 ms to a few hundred. Later calls with the same format, rounding mode and dtype reuse it. A convolution’s geometry and a block tensor’s shape are not part of the compiled kernel, so a new layer shape does not compile anything new.

Where rounding is applied#

A quantizer rounds a tensor, and a kernel rounds inside a reduction. The two compose, and MPTorch keeps them separate on purpose:

  • Quantizers covers the functions and objects that round a tensor:

    • elementwise: binaryK_quantize(), superfp_quantize(), Quant and Quantizer, which apply one rounding per element;

    • by blocks: block_quantize(), block_pack(), block_unpack() and BlockQuant, which choose one scale per block and then apply one rounding per element.

  • Quantized numerical kernels covers SplitMac, FusedMac, BlockMac, qmatmul(), block_matmul() and the convolutions. These apply one rounding per product and per addition, or per fused multiply-add, inside one matrix-product routine.

  • Layers covers QAffineFormats and the layers: which quantizer is applied to which signal, and which arithmetic each of a layer’s three matrix products runs in.
